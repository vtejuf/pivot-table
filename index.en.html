One core data flow, one set of extension mounts

The core does not depend on features. Dependencies always point from site / features → model / render; features only read core output and extend it through the mount points above. An architecture guard test blocks the core from importing features in reverse.

03 · matrix transform

One matrix multiplication locates every cell

A dimension hierarchy is a mixed-radix number: parents position coarsely, and children position finely inside the parent block. The whole tree collapses into one fixed matrix.

A record becomes an augmented vector. Each dimension contributes a member index id, followed by a constant 1: 

v = [i₁, i₂, ..., i_D, 1]ᵀ

Column d of matrix M is the unit vector of that dimension axis scaled by spand; the last column is the translation: 

[x, y]ᵀ = M · v

Parent and child spans multiply. Each step of a parent dimension crosses exactly the child member count times the child span: 

span_parent = n_child × span_child
span_d      = Π n_c (c is a descendant of d)

cartesian Default

Every parent member is padded with the full global set of child members, forming a regular grid. The span is independent of the parent, so the entire layout is one fixed matrix—at the cost of empty cells.

compact Compact

Only combinations that actually occur are placed, so parent blocks vary in size. There is no global fixed matrix, but each record still yields a piecewise affine transform.

  • Header member offset / size maps directly to rowspan / colspan.
  • Duplicate dimension combinations throw by default, forcing aggregation first instead of silently merging in the layout layer.
  • Each axis supports one hierarchy chain: a single root and at most one child per parent.

region > city > year

        [region] [city] [year] [1]
x  =  [   0       0      1     0 ] · v
y  =  [   3       1      0     0 ] · v
region span
3 = n_city × 1
city span
1
year span
1 · column axis

city has 3 members: each region step crosses 3 rows, and each city step crosses 1 row.

05 · performance

Cost follows the viewport, not the whole table

Scrolling iterates only over visible cells; headers are binary-pruned by offset; the canvas buffer is reused while dimensions stay unchanged; heatmap ranges are cached per layout.

22,500 Total cells in the 150×150 stress grid
50 Cells actually drawn in a 480×280 data viewport
1 Heatmap range scan per layout

What the renderer does

  • Viewport virtualization: iterate only the visible range; total cell count never enters the per-frame loop.
  • O(1) cell lookup: the model exposes cellMap.
  • Grid lines are merged into one beginPath() + stroke().
  • Header offsets are monotonic; binary search skips off-screen members and their subtrees.
  • The data area and two header bands are clipped separately, so frozen headers do not trigger a full redraw.
  • DPR transform is set once; the canvas buffer is not reset when dimensions are unchanged.

Trade-offs

  • Canvas 2D · current ~1k–100k cells; zero dependencies, fast batched text and rectangle drawing.
  • Canvas + offscreen cache Large tables with continuous scrolling; cache headers, grid, and zebra-stripe bitmaps.
  • WebGL / WebGPU 100k–1M cells with smooth zoom; text layout and hit testing cost more.
  • DOM / SVG Small tables, text selection, screen readers; performance drops sharply with many nodes.

Reading the numbers

  • Row depth mainly increases aggregation cost In this run the row grid reached at most 1,024 cells, and the matrix transform took 1.9–25.9 ms; most time went into grouping 1M detail rows.
  • Column depth doubles the grid With the row grid fixed at 1,024, every column level doubles the grid; the matrix transform grew from 75 ms to 2.74 s.
  • Memory hits the limit first Column depth 7 peaked at 744.8 MB; depth 8 OOMed on the 768 MB heap and did not finish, so the 3-second threshold was never reached.

Custom features

The core does not depend on features; pick a mount point and write a function that only reads core output.

  1. Pick a mount point Data derivation, layout derivation, render config, or post-render overlay.
  2. Write createXxx() Return cellStyle, draw, or a new display layout.
  3. Pass it to the core renderPivot / renderWithOverlay, without modifying the core.
